# ADR 0012 — SMS through MSG91 (decision D6)

**Status:** accepted 2026-11-06. D6 is decided: **MSG91**.

## How it works
- **One source of wording:** every SMS is a template in `backend/config/sms_templates.yml`. The text there is exactly what gets registered, because Indian DLT rules drop any SMS that doesn't match a registered template.
- **Code never sends free text:** it builds messages with `Adapters::Sms.message(:key, vars…)`. Each variable must be declared, and values are clipped to 30 characters (DLT's limit).
- **English only for now:** SMS text, including the category name, is English. Hindi and Punjabi need separate Unicode templates; add them if workers ask.
- **The adapter** (`lib/adapters/sms/msg91.rb`) uses MSG91's v5 flow API:
  - request: `POST https://control.msg91.com/api/v5/flow`, header `authkey`, body `{ template_id, short_url: "0", recipients: [{ mobiles: "91XXXXXXXXXX", code: "…" }] }`;
  - success means `type: "success"`.
- **Failures are classified:**
  - `rejected` (MSG91 refused: bad key, unapproved template, wrong variables) and `not_configured`: never retried.
  - `timeout`, `network`, `provider_error` (HTTP 5xx/429): retried. A login code retries briefly (3 attempts, 5 s apart; codes expire in 5 minutes).
- **A failed SMS never duplicates a notification:** it's logged, and the in-app notification and push still stand.
- **Production won't boot** with `SMS_ADAPTER=msg91` unless `MSG91_AUTH_KEY` and an MSG91 template id for **every** template are set (and never with `fake`, except staging).

## Settings
| Variable | What |
| --- | --- |
| `SMS_ADAPTER=msg91` | use MSG91 (`fake` in development/test/staging) |
| `MSG91_AUTH_KEY` | MSG91 → API → Auth key (a secret) |
| `MSG91_SENDER_ID` | only if the MSG91 templates use sender "FromAPI"; otherwise the template's sender is used |
| `MSG91_TEMPLATE_OTP`, `_LEAD_NEW`, `_QUOTE_ACCEPTED`, `_WORKER_APPROVED`, `_WORKER_CHANGES_REQUESTED`, `_WORKER_REJECTED` | the MSG91 template id for each message |

## Setting up MSG91 (one time, needs the business documents)
1. **DLT (TRAI):** register Workerly as a principal entity on a DLT portal (Jio, Vodafone Idea, Airtel, …).
   - Register a 6-letter **sender header** (e.g. `WRKRLY`).
   - Register **six transactional templates** with the texts in `sms_templates.yml`. Write each `%{name}` as `{#var#}`; the OTP template is in the "service implicit" or OTP category.
   - Approval usually takes a few working days.
2. **MSG91:** add the DLT entity ID, the header, and each approved template (with its DLT template ID). Name the variables as in our file: `##code##`, `##category##`, `##locality##`.
3. Put the auth key and the six MSG91 template ids into the environment (production: the app secret and `app_env`).
4. **Test before go-live:** run the API with these settings and `SMS_ADAPTER=msg91`, ask for a login code for your own number, and check MSG91's delivery report.

## Not done
- No live call has been made: there are no MSG91 credentials yet. The adapter is covered by specs against the documented request and response shapes. Confirm with one real code before launch (step 4).
- Delivery-report webhooks (DLR) are not consumed; MSG91's dashboard shows them.
- WhatsApp OTP, and voice OTP as a fallback.
